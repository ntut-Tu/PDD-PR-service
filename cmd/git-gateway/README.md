# git-gateway
> This document is generated by llm, please verify the content before using it.

REST service behind the PDD pull request page. It lists the open pull requests (GitHub) and
merge requests (GitLab) of the repositories bound to a PDD project, loads one pull request with
its commits and comments, and persists the fetched data and the provider tokens so that other
services (the test case agent) can read the same data after the user's JWT has expired.

Every provider call follows [ADR 0001](../../../docs/adr/0001-git-provider-request-strategy.md):
GraphQL with batching, TTL cache with stale fallback, quota reserve, bounded retries and a
per-token concurrency cap. The browser never talks to GitHub or GitLab.

## How it works

1. The caller sends the PDD login JWT (`Authorization: Bearer <jwt>`). The gateway verifies the HS256
   signature and the expiry with the key derivation of the legacy backend (`base64url(pdd.jwtSecret)`
   as raw key bytes) and reads `sub` (account) and `oauth` (GitHub or GitLab access token).
2. The `oauth` token is stored, encrypted with AES-256-GCM, under the account in SQLite.
3. Project access is checked with `GET /project/` of the PDD backend using the caller's JWT
   (`403` when the project is not in the list). Repositories come from `GET /repo/{projectId}`:
   a `github.com` URL is GitHub, any other entry with owner and name and no `type` is a GitLab project
   on the host of its URL. Both lookups are cached for `pdd.backend.cacheTTL`.
4. The provider is called with the `oauth` token. A token the provider rejects (`401`, for example
   a GitLab login used on a GitHub repository) is reported for that repository only.

## Public API

All endpoints need `Authorization: Bearer <PDD JWT>`. JSON, camelCase. Behind Traefik the prefix
`/git-gateway` is stripped, so the browser calls `/git-gateway/api/v1/...`.

### `GET /api/v1/projects/{projectId}/pulls`

```json
{
  "pulls": [
    {
      "repoId": 12, "provider": "github",
      "repo": {"owner": "octo", "name": "hello", "url": "https://github.com/octo/hello"},
      "number": 42, "title": "Fix login", "state": "open", "draft": false, "mergeable": "mergeable",
      "author": {"login": "alice", "avatarUrl": "https://..."},
      "sourceBranch": "fix-login", "targetBranch": "main",
      "headSha": "9b1c0f2e5d7a4c3b8e6f1a2d3c4b5a69788796a5",
      "url": "https://github.com/octo/hello/pull/42", "updatedAt": "2026-10-24T10:00:00Z"
    }
  ],
  "stale": false,
  "fetchedAt": "2026-10-24T10:01:00Z",
  "errors": [
    {"repoId": 13, "repo": "pdd/backend", "code": "upstream_failed", "message": "..."}
  ]
}
```

* `mergeable` is `mergeable`, `conflicting` or `unknown`.
* `headSha` is the commit at the tip of the source branch (GitHub `headRefOid`, GitLab `diffHeadSha`).
* The list is always `200` when the caller may see the project. A failing repository is reported in
  `errors` and does not hide the others. `code` is `upstream_failed`, `quota_reserve` or
  `provider_unauthorized`.
* `stale` is `true` when at least one repository was served from stale cache because the provider
  could not be asked (quota in reserve, or failures after the retry budget). Those repositories also
  appear in `errors` with the reason. `fetchedAt` is the oldest time the provider confirmed the data.

### `GET /api/v1/projects/{projectId}/repos/{repoId}/pulls`

The same response as the project list, for one repository: only that repository is requested from
the provider (one batch of one). `404 not_found` when `repoId` is not a GitHub or GitLab repository
of the project; project membership is checked as for the other endpoints. The project list above stays
for compatibility.

### `GET /api/v1/projects/{projectId}/repos/{repoId}/pulls/{number}`

```json
{
  "pull": {
    "...": "all PullSummary fields",
    "baseSha": "commit of the target branch the pull request is based on",
    "description": "markdown",
    "commits": [{"sha": "...", "message": "...", "author": "...", "committedAt": "RFC3339", "url": "..."}],
    "comments": [{"id": "...", "author": {"login": "...", "avatarUrl": "..."}, "body": "markdown", "createdAt": "RFC3339"}]
  },
  "stale": false,
  "fetchedAt": "2026-10-24T10:01:00Z"
}
```

At most 100 commits and 100 comments are returned. GitLab system notes are dropped.

### `GET /api/v1/projects/{projectId}/repos/{repoId}/pulls/{number}/files`

The files changed by the pull request, for preselecting production code in the test generation panel.
Same body as the internal files endpoint below plus `stale` and `fetchedAt`, read with the caller's
own provider token:

```json
{
  "headSha": "<40-hex>", "baseSha": "<40-hex>",
  "files": [{"path": "src/A.java", "previousPath": "", "status": "added", "additions": 2, "deletions": 0, "patch": "@@ ..."}],
  "truncated": false, "stale": false, "fetchedAt": "2026-10-24T10:01:00Z"
}
```

### `GET /api/v1/projects/{projectId}/repos/{repoId}/pulls/{number}/tree`

The repository tree at the head commit of the pull request, for choosing files as test generation
context.

```json
{
  "ref": "9b1c0f2e5d7a4c3b8e6f1a2d3c4b5a69788796a5",
  "entries": [{"path": "src/main/java/a/B.java", "type": "blob", "size": 123}, {"path": "src", "type": "tree", "size": 0}],
  "truncated": false,
  "stale": false,
  "fetchedAt": "2026-10-24T10:01:00Z"
}
```

* `type` is `blob` or `tree`; submodules are left out. GitLab does not report sizes, so `size` is `0`.
* `truncated` is `true` when the provider cut the tree (GitHub, very large trees) or the page cap
  `files.maxPages` of 100 entries each was reached (GitLab).

### Errors

Every error has the form `{"error": {"code": "...", "message": "..."}}`.

| Status | `code` | Meaning |
| --- | --- | --- |
| 401 | `unauthorized` | Missing, malformed, badly signed or expired JWT (internal API: wrong `X-Internal-Token`) |
| 403 | `forbidden` | The caller is not a member of the project |
| 400 | `bad_request` | Internal API: a required query parameter is missing |
| 404 | `not_found` | Unknown project, repository of another project, pull request, file or ref |
| 502 | `upstream_failed` | The provider (or the PDD backend) failed after the retry budget and nothing is cached |
| 502 | `provider_unauthorized` | The provider rejected the caller's token (detail endpoint) |
| 503 | `quota_reserve` | Quota below the reserve threshold and nothing is cached |

## Internal API

For other PDD services; not exposed through Traefik.

`GET /internal/v1/projects/{projectId}/repos/{repoId}/pulls/{number}?account=<pdd account>`
with header `X-Internal-Token: <security.internalToken>` (constant-time comparison).

The response equals the public detail endpoint. The request uses the provider token stored for
`account` (the token of that account's latest authenticated request) and is served from the persisted
cache while it is fresh; otherwise the gateway refreshes it upstream under the same policy. `404` when
no token is stored for the account. Project membership is not checked: callers are trusted services.

### Repository content endpoints

All three use the same authentication as above (`X-Internal-Token`, `?account=`) and the provider
token stored for the account. Because the caller has no user JWT, the gateway cannot ask the PDD backend
whether the account is a member of the project; it only checks that the repository belongs to the
project and relies on the provider permissions of the stored token. Only trusted services may reach
these endpoints: Traefik does not route `/git-gateway/internal/` (see `pdd_deploy_tools/traefik/dynamic/pdd.yaml`),
so they are reachable on the Docker network only.

`GET /internal/v1/projects/{projectId}/repos/{repoId}/pulls/{number}/files?account=<account>`

```json
{
  "headSha": "<40-hex>", "baseSha": "<40-hex>",
  "files": [{"path": "src/A.java", "previousPath": "", "status": "added", "additions": 2, "deletions": 0, "patch": "@@ -0,0 +1,2 @@\n+a\n+b"}],
  "truncated": false
}
```

`status` is `added`, `modified`, `removed` or `renamed` (`previousPath` is set for renames). `patch` is
empty for binary or very large files, which the provider sends without a diff. The patches of one pull
request share the `upstream.maxBodyBytes` budget: patches that no longer fit are emptied and `truncated`
is `true`, which is also set when the provider has more files than `files.maxPages` pages of 100.
GitLab reads `merge_requests/:iid/diffs`, so GitLab 15.7 or later is required; additions and deletions
are counted from the diff.

`GET /internal/v1/projects/{projectId}/repos/{repoId}/tree?account=<account>&ref=<sha>` returns the same
body as the public tree endpoint for any commit `ref`.

`GET /internal/v1/projects/{projectId}/repos/{repoId}/files?account=<account>&ref=<sha>&path=<path>`

```json
{"ref": "<sha>", "path": "src/A.java", "size": 123, "content": "<utf-8 text>", "binary": false, "truncated": false}
```

A file containing a NUL byte or invalid UTF-8 is `binary` and has an empty `content`. Text longer than
`files.maxBytes` is cut on a character boundary and `truncated` is `true`; `size` is always the whole
size. `400 bad_request` when `account`, `ref` or `path` is missing. A file larger than
`upstream.maxBodyBytes` is rejected by the request policy and answered with `502 upstream_failed`.

Trees, files and diffs go through the request policy of ADR 0001: REST with ETag revalidation, cached
for `cache.ttl.tree`, `cache.ttl.file` and `cache.ttl.prDetail` respectively, quota reserve and bounded retries.

## Health

`GET /healthz` returns `200 {"status":"ok"}` when the database answers, `503` otherwise. No authentication.

## Configuration

Hierarchical YAML in Helm-values style. The defaults live in the fully commented
[`values.yaml`](../../internal/gitgateway/config/values.yaml), which is embedded into the binary.
Pass your own file with `--config <file>`; it only needs the keys you change. The flag can be
repeated, later files are deep-merged over earlier ones (maps merge key by key, scalars and lists
replace). There is no environment variable configuration.

The service refuses to start on unknown keys, wrongly typed values, invalid durations (Go syntax:
`500ms`, `30s`, `24h`) or missing required values, and reports every problem at once with its YAML path:

```text
git-gateway: invalid configuration:
pdd.jwtSecret: required
security.tokenKey: required
retry.maxAtempts: unknown key
```

### Required values

Three values have no default and must be set:

| YAML path | How to get it |
| --- | --- |
| `pdd.jwtSecret` | The secret the PDD backend signs login JWTs with: the string in `backend/src/main/java/com/JwtHelper.java`. Copy it as is and do not commit it. |
| `security.tokenKey` | Base64 of a 32-byte AES-256 key: `openssl rand -base64 32` |
| `security.internalToken` | Shared secret of the internal API: `openssl rand -hex 32` |

```yaml
pdd:
  jwtSecret: "<secret from JwtHelper.java>"
security:
  tokenKey: "<output of openssl rand -base64 32>"
  internalToken: "<output of openssl rand -hex 32>"
```

## Run locally

```bash
cd services
cat > .local.yaml <<YAML
pdd:
  jwtSecret: dev-secret
  backend: {url: "https://localhost:5005", insecureTLS: true}
security:
  tokenKey: "$(openssl rand -base64 32)"
  internalToken: "$(openssl rand -hex 32)"
storage:
  dataDir: $PWD/.data
YAML
go run ./cmd/git-gateway --config .local.yaml
curl localhost:8080/healthz
```

Container (build context is `services/`). The image starts with
`--config /etc/pdd/git-gateway/values.yaml`; mount your merged file there:

```bash
docker build -f images/git-gateway/Dockerfile -t pdd/git-gateway services
docker run --rm -p 8080:8080 -v pdd-git-gateway-data:/data \
  -v "$PWD/.local.yaml:/etc/pdd/git-gateway/values.yaml:ro" pdd/git-gateway
```

The image runs as a non-root user; `/data` is owned by that user, so a new named volume is writable.

## Known limitations

* A GitLab server whose GraphQL schema lacks the fields of the ADR queries is not served; the REST
  fallback of the ADR is not implemented.
* A GitHub list batch containing a repository the token cannot see is answered with GraphQL errors
  and is therefore not cached (ADR: responses with `errors` are never cached), so such a batch is
  queried again on every request.
* Cache entries are per token; a new login token starts with a cold cache.
* GitLab merge request files need the `diffs` endpoint (GitLab 15.7 or later); the older `changes`
  endpoint is not used.
