# sandbox-controller
> This document is generated by llm, please verify the content before using it.

Go service that compiles and runs generated JUnit tests against the head commit of a pull
request inside a gVisor (`runsc`) container, and reports what happened. The test agent never
touches the container runtime: it creates a **SandboxRun** over HTTP and reads its status. The
architecture is [ADR 0003](../../../docs/adr/0003-sandbox-architecture.md); the runtime (containerd
inside the controller's own container) is [ADR 0004](../../../docs/adr/0004-sandbox-runtime-containerd.md).
This page documents the implementation.

## How it works

A `SandboxRun` is one try: an immutable `spec` (account, project, repository, head SHA, the
generated test files, the test classes) and a `status` that only the controller changes. Records
live in SQLite (`sandbox-controller.db`). A fixed try is a new run, so every try is kept.

The reconcile loop runs on every create / delete and every `reconcile.resyncInterval`. It compares
the records with the containers labelled `pdd.sandbox/run=<id>` and the directories below
`workspace.dir`:

| Observed | Action |
| --- | --- |
| `Pending`, running count below `limits.maxConcurrent` | `Preparing`: check `runsc`, download the archive from git-gateway, unpack it, write the test files, detect the build tool, write the proxy configuration; then create and start the container and set `Running` |
| `Pending`, at the limit | nothing, the run waits |
| `Running`, container exited | read the JUnit XML reports and the log, set `Succeeded` or `Failed`, remove the container |
| `Running`, past `limits.timeout` | stop and remove the container, `Failed` / `timeout` (partial result kept) |
| `Preparing` or `Running`, container missing | `Error` / `internal` (host or controller restart) |
| `Preparing`, container exists (crash after start) | adopt it: `Running` |
| container or workspace without an active record | removed |
| terminal and older than `retention.workspace` | workspace removed, record kept |
| `deletionRequested` | container and workspace removed, then the record |

Preparation (the download) runs in a background goroutine per run so that one slow download never
delays the timeout checks of the others. Every step is idempotent, so a crash at any point is
repaired by the next pass. Runs keep going while the controller is down; the next process adopts
the containers (`Running` runs are finished, expired ones time out).

If listing the containers fails, the loop does not touch containers, workspaces or deletions in
that pass (it must not remove what it cannot see); `Pending` runs still get their `runsc` check.

### Phases and reasons

| Phase | Reason | Meaning |
| --- | --- | --- |
| `Succeeded` | | the project compiled and every listed test class ran and passed (build exit code 0) |
| `Failed` | `compile_failed` | nothing compiled, or the build failed before any test ran (for example an unresolvable dependency); `result.compiled` is `false` and the error lines of the output are kept |
| `Failed` | `tests_failed` | a requested class failed, did not run or has no report; also out-of-memory kills |
| `Failed` | `timeout` | `limits.timeout` exceeded |
| `Error` | `sandbox_unavailable` | containerd is unreachable, `runsc` is not installed, or the sandbox network cannot be trusted: the CNI plugins are missing or `net.ipv4.ip_forward` cannot be set to `0` |
| `Error` | `unsupported_project` | no `pom.xml` / `build.gradle(.kts)` in the repository root |
| `Error` | `source_unavailable` | git-gateway answered an error or the archive is unusable or unsafe |
| `Error` | `internal` | anything else |

## Internal API

All `/internal` endpoints need `X-Internal-Token` (constant-time comparison) and must not be routed
by Traefik. Errors use the git-gateway shape `{"error": {"code": "...", "message": "..."}}` with
codes `invalid_request` (400, 413), `unauthorized` (401), `not_found` (404) and `internal` (500).

### `POST /internal/v1/runs` -> `201`

```json
{"spec": {
  "account": "alice", "projectId": 7, "repoId": 1, "headSha": "<40 lowercase hex>",
  "files": [{"path": "src/test/java/a/BTest.java", "content": "..."}],
  "testClasses": ["a.BTest"]
}}
```

Validation: `files[].path` must be relative, free of `..` and lie below a `src/test` directory (of
the root or of a module); `testClasses` are 1-200 fully qualified class names (they become build
arguments, no shell is involved); at most 200 files and 4 MiB of content. The answer is the run:

```json
{
  "id": "run_0123456789abcdef01234567",
  "spec": { "...": "as sent" },
  "status": {
    "phase": "Pending",
    "message": "waiting for a free sandbox",
    "conditions": [],
    "createdAt": "2026-10-24T12:00:00Z"
  },
  "deletionRequested": false
}
```

A finished run additionally has `reason`, `buildTool` (`maven` or `gradle`), `startedAt`,
`finishedAt` and

```json
"result": {
  "compiled": true,
  "tests": [{"class": "a.BTest", "passed": 3, "failed": 1, "errors": 0, "skipped": 0}],
  "output": "build and test output, truncated to output.maxBytes (the end is kept)"
}
```

`conditions` lists the completed steps: `Prepared`, `Started`, `Completed`.

### `GET /internal/v1/runs/{id}` -> `200` with the run, `404` when unknown or already deleted.

### `DELETE /internal/v1/runs/{id}` -> `202`; the container, the workspace and then the record are removed asynchronously.

### `GET /healthz` -> `200 {"runsc": true|false}` (`503` when the database does not answer). No authentication.

## Source, workspace and build

* The controller calls
  `GET {gitGateway.url}/internal/v1/projects/{p}/repos/{r}/archive?account=<account>&ref=<sha>` with
  `X-Internal-Token: <gitGateway.internalToken>`. The provider token never leaves git-gateway.
* The tar.gz is unpacked below `<workspace.dir>/<run id>/src` with its single top-level directory
  removed. Entries with `..`, absolute names, hard links and symbolic links that point out of the
  tree are rejected, special files are skipped, nothing is written through a symbolic link, and
  `workspace.maxBytes` / `workspace.maxFiles` cap the unpacked size and entry count. A problem ends the
  run as `source_unavailable`.
* The generated files are written under `src/test` (again without following symbolic links).
* Detection: `pom.xml` -> Maven, otherwise `build.gradle` / `build.gradle.kts` -> Gradle,
  otherwise `unsupported_project`. `mvnw` / `gradlew` is used when the wrapper files are present
  (Gradle also needs `gradle-wrapper.jar`).
* Commands (no shell, the classes are separate arguments):
  * `mvn -B -ntp -s /workspace/.pdd/settings.xml test -Dtest=<classes> -Dsurefire.failIfNoSpecifiedTests=false -DfailIfNoTests=false`
  * `gradle test --no-daemon --console=plain -I /workspace/.pdd/init.gradle --tests <class> ...`
    (the init script sets `failOnNoMatchingTests = false` for multi-module builds)
* Results come from the JUnit XML in `**/surefire-reports/TEST-*.xml` and
  `**/build/test-results/**/TEST-*.xml` (symbolic links are not followed). Nested classes
  (`Outer$Inner`) count for `Outer`.

## Container and network

* `runsc` only. It is checked at the start of every run; without it the run ends as
  `sandbox_unavailable` and nothing is downloaded.
* Mounts: `<workspace.dir>/<run id>` at `/workspace` and the repository's dependency cache at
  `/cache` (`HOME=/cache/home`, so `.m2` and `.gradle` live there). Nothing else from the host.
* Non-root user (`limits.user`), `no-new-privileges`, all capabilities dropped, read-only root file
  system with a `tmpfs` `/tmp`, PID limit, CPU and memory limits (swap equal to memory), a private
  `/etc/hosts` (without it nothing resolves `localhost`).
* The **cache directory is `<cache.dir>/<projectId>/<repoId>`**. The run spec carries no provider or
  repository path, so the ids are used; two PDD projects that use the same repository get separate
  caches.
* The controller serves an allow-list HTTP proxy on `network.proxy.listen`:
  * `CONNECT host:443|80` is tunnelled and absolute-URI `http://` requests are forwarded, only for
    hosts in `network.allowedHosts` (`*.example.com` matches subdomains). Everything else gets `403`.
  * Maven gets the proxy through `settings.xml` plus `MAVEN_OPTS` system properties, Gradle through
    `GRADLE_OPTS` system properties.
  * The sandboxes reach the proxy at `network.proxy.host`; when empty it is the host end of the sandbox link (see [Runtime](#runtime-containerd)).

### Runtime `containerd`

containerd, the runc v2 shim, `runsc` and the CNI plugins run in the same container as the
controller (image `pdd/sandbox-controller`, see [Runtime container](#runtime-container)); no host
container engine is used. Sandboxes live in the containerd namespace `runtime.containerd.namespace`.

* **OCI runtime.** `runtime.containerd.shim: runc` (default) starts `io.containerd.runc.v2` with
  `runsc` as its runtime binary (`runtime.containerd.runscPath`), which works inside a
  container; `runsc` uses `containerd-shim-runsc-v1` instead, which inside a
  container can fail with "failed to set OOM Score on shim: permission denied". The
  reconcile loop asks for the OCI runtime `runsc`; the name `runc` (plain runc, no gVisor) exists for
  tests only.
* **Images** are pulled by containerd on first use (public registries, no credentials) and
  unpacked with the overlayfs snapshotter; an image that is already in the namespace is not pulled.
* **Network.** Every sandbox gets its own network namespace (files in `runtime.containerd.netnsDir`)
  connected by CNI: a `ptp` veth pair, a `host-local` address from `runtime.containerd.cni.subnet`
  (leases in `cni.dataDir`) and `loopback`. There is no masquerade. `ptp` gives the host end of
  every veth the first address of the subnet (`10.213.0.1` by default) and adds a route for
  the subnet through it but no default route, so a sandbox reaches that address, where the proxy
  listens on all interfaces, and nothing else: other sandbox addresses are routed to the runtime
  container and dropped there (firewall, forwarding off), anything else is "network unreachable".
  `network.proxy.host` defaults to that first address.
* **Firewall.** `EnsureNetwork` (before every start) and every network setup install, idempotently
  (`-C` checks, under the setup lock), iptables rules in the runtime container, so they hold before
  any sandbox exists: `FORWARD` drops everything from and to the subnet, and `INPUT` accepts from the
  subnet only established/related packets and TCP to the proxy port (`network.proxy.listen`), then
  drops. The sandboxes therefore cannot reach the API port or any other port of the runtime
  container, nor each other, even if forwarding is on. For IPv6 (link-local only) everything the
  `veth*` links send to or through the runtime container is dropped. The rules live in the chains
  `PDD-SANDBOX-IN` and `PDD-SANDBOX-FWD`; a chain that differs from the wanted rules (a changed proxy
  port) is rebuilt. Without `iptables` (the image installs it, nft backend) or when a rule cannot be
  installed, the run ends as `sandbox_unavailable`.
* **Forwarding.** `ptp` switches `net.ipv4.ip_forward` on for every sandbox it sets up. The runtime
  writes `0` back after each setup and `EnsureNetwork` refuses with `sandbox_unavailable` when it
  cannot make the value `0`. This is a second layer behind the firewall; setups are serialized, so
  the value is `1` for the duration of one `ptp` call at most.
* **Output** of a container goes to `<runtime.containerd.logDir>/<container>.log` (written by the
  shim, not capped; the run timeout bounds it). The log file, the hosts file, the network namespace,
  the address lease, the task and the snapshot are removed with the container.
* **OOM kills.** `OOMKilled` is set when the `oom_kill` counter of the container's cgroup
  (`memory.events`, or `memory.oom_control` on cgroup v1) is above zero. The kernel kills the
  sandbox when it exceeds its limit under gVisor as well (the tests check this); it is a counter
  of the cgroup, not an event, so it is reliable as long as the task exists.
* **Restart.** containerd's tasks die with the runtime container. A container without a task is
  reported as `created`, so a `Running` run finds a container that "never started" and ends as
  `Error` / `internal`, and the stale container, log and workspace are then removed.
* **Concurrency.** Operations on the same container are serialized; the others run in parallel.
  Image pulls are shared.

## Deployment notes

### Runtime container

The image is built from the `services/` directory:

```bash
docker build -f images/sandbox-controller/Dockerfile -t pdd/sandbox-controller services
```

It holds the controller, containerd and its runc v2 shim (built at the version of the containerd Go
client in `go.mod`), `runsc` from the gVisor apt repository (`/usr/bin/runsc` with its `gvisor-bin`
helpers), `iptables` and the CNI plugins `ptp`, `host-local` and `loopback`. The entrypoint mounts tmpfs on
`/run/containerd` and `/run/pdd-sandbox`, prepares the cgroup, starts containerd, waits for its socket
and runs the controller with the given arguments; when either process exits the container exits with
its status, and SIGTERM goes to both. The container must run **privileged** with a **private cgroup
namespace**, and `/var/lib/containerd` must be a volume (the overlay snapshotter cannot run on the
container's own overlay file system):

```bash
docker run -d --name pdd-sandbox-controller --restart unless-stopped \
  --privileged --cgroupns=private \
  -v sandbox-controller-data:/data \
  -v sandbox-containerd:/var/lib/containerd \
  -v sandbox-state:/var/lib/pdd-sandbox \
  -v "$PWD/sandbox-controller.yaml":/etc/pdd/sandbox-controller/values.yaml:ro \
  pdd/sandbox-controller
```

* `/var/lib/pdd-sandbox` holds the workspaces, the dependency caches and the logs (the defaults of
  `workspace.dir`, `cache.dir` and `runtime.containerd.logDir`). The paths are inside the runtime
  container; no host path has to match.
* The image runs as root: containerd, the shim and `runsc` create namespaces, mount and write cgroups,
  and the controller writes workspaces that the sandbox user (uid 1000) must be able to use. The
  sandboxes it starts are unprivileged and run under gVisor.
* A sandbox that escapes gVisor and then the privileged runtime container reaches the Docker
  (Desktop) VM; ADR 0004 lists this trade-off. Of the runtime container the sandboxes reach only
  the proxy port, on the first subnet address (firewall above).
* Build images are stored a second time, in the `/var/lib/containerd` volume; the first run of each
  build tool takes longer.
* The entrypoint expects the `containerd.toml` of the image (socket `/run/containerd/containerd.sock`,
  the default of `runtime.containerd.address`).

### Required values

`security.internalToken` (protects this service's API; the test agent sends it) and
`gitGateway.internalToken` (the token git-gateway expects for the archive call, equal to its
`security.internalToken`). They are different secrets. Everything else has a default.

## Configuration

Same mechanism as the other services: hierarchical YAML in Helm-values style, defaults in the fully
commented [`values.yaml`](../../internal/sandboxcontroller/config/values.yaml) embedded in the
binary, `--config <file>` (repeatable, later files deep-merge over earlier ones; maps merge, scalars

## Tests

```bash
go test ./...            # unit tests and the integration test with a fake runtime and a fake git-gateway
go test -race ./internal/sandboxcontroller/...
```

`internal/sandboxcontroller/runtime/containerd/integration_test.go` (build tag `containerdit`) tests
the containerd runtime against a real containerd with `runsc`: create, start, inspect, logs, stop,
remove, list, limits in the cgroup, gVisor in the guest (`dmesg`), OOM kills, network isolation (the
sandbox reaches the proxy port on the host end of its link, but not another port there (the API), an
external address or another sandbox, the last also while `ip_forward` is forced to 1) and the cleanup of namespaces, leases, logs and
veth links. It needs root, `iptables`, the CNI plugins and a running containerd, so it runs inside the runtime
container: build the test binary on the host and run it in a running container of the image
(started as above, with a volume on `/var/lib/containerd`):

```bash
CGO_ENABLED=0 go test -c -tags containerdit -o containerd.test ./internal/sandboxcontroller/runtime/containerd
docker cp containerd.test pdd-sandbox-controller:/tmp/containerd.test
# the sandbox image must be in the test namespace (here from the local Docker image store)
docker save ubuntu:24.04 | docker exec -i pdd-sandbox-controller ctr -n pdd-sandbox-it images import -
docker exec pdd-sandbox-controller /tmp/containerd.test -test.v
```

The image needs `ctr` only for the import (it is not part of the image: copy it in, or import the
image another way). Environment: `PDD_IT_CONTAINERD` (socket), `PDD_IT_NAMESPACE` (default
`pdd-sandbox-it`), `PDD_IT_RUNTIME` (`runsc`, or `runc` to run without gVisor), `PDD_IT_RUNSC`,
`PDD_IT_IMAGE` (needs bash, coreutils and `dmesg`; default `docker.io/library/ubuntu:24.04`),
`PDD_IT_CNI_BIN`, `PDD_IT_SUBNET`. The tests are skipped when the socket or the OCI runtime is missing.
The pull of a missing image is not part of them (it needs a registry).
